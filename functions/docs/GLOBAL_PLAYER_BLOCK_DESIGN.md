# 全モード共通プレイヤーブロック 設計・実装仕様

作成日・実装日: 2026-09-14 / バージョン: global-player-block-v1

対象: 貼り合いスタジアム。本書は共通ブロックの設計と実装方針を定める。本番の配信検証は `PLAYER_SAFETY_RELEASE_QA.json`、画面検証は `PLAYER_SAFETY_UI_QA.json` に記録する。

## 実装した公開境界

- 常設の「安心設定」から一覧と解除を開く。各対戦・交流画面と公開プレイヤー表示にも操作を置き、直前の相手を24時間参照できる。顔なじみ帳の公開段階には依存しない。
- `playerSafetyAction` を App Check 必須の共通 Callable とし、ブロック・解除・一覧・操作の再試行・公開表示・コメントを処理する。戦略型の部屋作成と受諾も同じサーバー境界に移した。
- Firestore の方向別ポリシーと、RTDB の部屋・試行ごとの接続許可を照合する。解除で古い接続許可を復活させない。終了処理は永続 outbox から冪等に再試行する。
- ランキングコメントの旧RTDB経路は有効化後に直接読み書きできない。サーバー経由で旧記録を読み、共通ポリシーで絞り込む。新しいコメントと削除記録は非公開Firestoreに保存し、旧コメントが再表示されることを防ぐ。
- 移行は `scripts/migrate-player-safety.js` の読み取り専用実行を先に行い、`--apply` を指定して旧ブロックの和集合を取り込む。確定した解除を再移行で上書きしない。現在の参加者ポインターが一致する部屋だけ接続許可を補い、過去の対戦記録全体は移行しない。
- 公開順は互換性を保つ Rules・Indexes、関連 Functions、移行、Hosting と Worker の配信確認、最後に `online/config/playerSafetyEnabled=true`。切り替え中は canonical 未作成の相手についてのみ旧ブロックを参照する。

## 1. 目的と保証範囲

プレイヤーが一度ブロックすれば、同じアカウントの相手と、別モードを通じて再び対戦・交流・新規取引することを防ぐ。理由の入力、通報、相手の同意、顔なじみ登録、試合完走、課金は必要としない。

基本仕様:

- AがBをブロックした場合、AとBの新しい対戦・交流・取引を両方向で止める。BがAをブロックした場合も同じ。
- 適用はFirebase AuthenticationのUID単位。名前変更や同じUIDの別端末復元でも維持する。別アカウントまで同一人物と推測して巻き込まない。
- 顔なじみ帳の公開段階とは独立した共通機能にする。顔なじみ・再会優先を有効化する必要はない。
- 有効期限や待機時間で自動解除しない。検索条件を広げてもブロックは緩めない。
- 相手へブロック通知・理由・実施者・被ブロック件数を返さない。少人数時の状況などから推測される可能性まで否定しない。
- ブロック数をRATE、報酬、ランキング評価、処罰の根拠に直接使わない。通報とブロックは別の操作として扱う。
- サーバーで有効化された後の新しい接触を拒否する。保存中・反映中・完了を区別し、未完了を成功表示しない。
- 公式クライアントでは操作直後に受信表示・再生とP2P接続を閉じられる。サーバーの権限失効で既に成立した任意のWebRTC接続を物理的に切断したり、受信済みデータ・スクリーンショットを消したりできるとは約束しない。

顔なじみ帳は、双方が希望して成立する関係の帳面であり、再会優先まで有効なら、双方が希望して同時待機する相手を優先する機能である。添付画像から確認できるのは入口の非表示までで、サーバー設定が無効なのか取得失敗なのかは未確認。本書ではその設定を変更しない。

## 2. モード・接点別の動作

| モード・接点 | ブロック後に止めること | 保持すること |
| --- | --- | --- |
| 通常型1on1 | 通常検索、再会優先、招待の承諾、古い招待の再利用、対戦中・結果後の新しい交流 | サーバー確定済みの勝敗・RATE・実績・報酬処理 |
| 戦略型1on1 | マッチング、承諾、再接続、対戦後の品評会・チャット・メディア交換 | 確定済みの結果・証跡 |
| 貼り合い自由卓 | 双方の部屋一覧、来訪札、招待URLからの入室、受け入れ、再接続、しおり・縁からの再接触 | 本人の部屋・成長等の既存データ |
| 推し値市場 | 一般・常連優先待機、商店指定、商談開始、再接続、新規営業・延長・購入、推薦や常連帳からの接触 | 成立済み売買・証書・実績・台帳、預かり金の精算 |
| AnjuPayフリマ | 双方への新しい出品表示、新規購入、推し帳への追加・再接触導線 | 成立済みの出会いの記録・双方レシート・残高・実績 |
| AI文字コラ台本販売 | ブロック関係にある作者・利用者間の新規有料利用、公開棚・作者導線 | 支払済み利用分の保存済み台本、従来条件内の再開・終了・通報、売上 |
| ルーレットの作者パック | ブロック関係にある作者・利用者間の新規購入、公開棚・作者導線 | 購入済み改訂・支払済み利用分のスナップショット、従来条件内の利用・終了・通報 |
| 対戦後の差し入れ | 双方向の新しい送金 | 成功済み送金、履歴、同じ成功結果の再取得 |
| ランキングコメント | 双方向の新規投稿・更新、本人向けの相手コメント表示 | 自分の投稿や自分の欄の削除権限、必要な既存記録 |
| 推しカード・各モードの公開作者/商店紹介 | ログイン中の本人向け一覧での露出、X等のプロフィール導線、新しい関係操作 | 自分のカード編集、既存購入記録に保存された情報、公開済み外部共有物 |
| 総合・市場・作者・断惑NOTE等のランキング | 本人向け画面での相手の名前・紹介文・X・コメント・接触導線の表示 | 正本の順位・数値・母集団・入賞記録・本人の記録 |
| AI相手の練習、端末内の運動、断惑NOTEの非公開記録 | 他のプレイヤーとの接点にだけ適用 | 一人用のプレイ・記録・購入済み公式アイテム |
| 終了したteam・royale・鍛え合い等 | 過去画面の接触導線が残る場合にのみ共通判定 | 履歴。新しい対戦モードとして復活させない |

フリマと推し値市場の売買は、現行仕様では画像データ・物品・著作権を引き渡すものではない。フリマは出会いの記録、市場は証書等を保持する。AI台本・ルーレットの購入済み利用分とは分けて扱う。

購入済み利用分の保持は、使い切りを買い切りに変更したり、既存の期限・回数制限を延ばしたりする意味ではない。新たな課金が必要な次回利用は拒否する。支払済み利用の終了に付随する正当な既存精算は完了させる。

## 3. 公開情報と非表示の境界

本機能の中心は同一アカウント間の新しい接触の防止である。公開ランキングや外部共有済みURLから相手の存在を完全に消す機能とは説明しない。

- ログイン中の公式画面では、共通サービスが返す本人向け表示を使う。通常の棚は対象を除外する。
- ランキングは順位を詰め直さない。必要なら「非表示のプレイヤー」と数値だけを残す表示にし、名前・自由記述・X・コメントボタンを出さない。非表示人数やブロックが理由であることは他人に返さない。
- コメント本文は認証済み・閲覧者別の取得へ移す。A/B間だけでなく、Aが第三者Cの欄を見る場合も、Bによる自由記述はAに返さない。
- 過去のコメントはブロックだけで全利用者から削除しない。欄の持ち主・投稿者の既存削除操作は引き続き利用できる。
- 正本順位、公開済みの名誉記録、ログアウト状態の公開情報、X等の外部情報まで非公開になるとは保証しない。
- 自由卓の公開招待プレビューは現在認証ユーザー別の表示ではない。公開概要が見えても、来訪・入室はサーバーで必ず拒否する。認証済みの詳細・入室導線には共通判定を適用する。
- 新しい公開IDを作り直しても回避できないよう、作者・店主・カード等は内部の所有者UIDで判断する。表示名で所有者を推測しない。

## 4. 画面と操作

### 常設入口

タイトル画面の共通メニューに「安心設定」を追加し、その中に「ブロックしたプレイヤー」を置く。各モードのメニューから同じ管理画面へ開ける。ウォレット残高、顔なじみ人数、ランキング参加状態には依存させない。

### 相手ごとの入口

- 対戦・同席・商談中: 常に到達できる相手メニューに「退出する」「ブロックして退出」を置く。
- 試合結果・途中終了画面: 「この相手をブロック」。完走や顔なじみ登録を要求しない。
- 商店・出品・台本・パック・コメント・カード: 「このプレイヤーをブロック」。対象の所有者をサーバーが確定する。
- 画面を閉じたあとでも、直前相手の短期参照から操作できる。新しい公開対戦履歴一覧は作らない。

通常の確認文案:

> このプレイヤーをブロックしますか？
> すべてのモードで、この相手との新しい対戦・交流・購入を停止します。相手に通知は届きません。確定済みの戦績・購入記録・購入済みの利用分は残ります。

進行中の市場では、既存の着手料・預かり金の扱いを短く併記する。精算額の取得失敗で退出を妨げない。「必ず全額返金」とは表示しない。

### ブロック一覧

本人が自分で登録した相手だけを表示する。保存時の表示名、本人の登録日時、解除操作を返し、現在のオンライン状態、現在名の追跡、相手側の選択、UID、被ブロック件数は返さない。同名の相手は日時・登録元の表示で区別し、解除は表示名ではなく本人用ランダムIDで行う。

解除しても相手側のブロックは残る。顔なじみ・常連・しおり・推薦は自動復活させず、新しい本人の選択を必要とする。解除前の招待や終了したセッションも復活させない。

### 通信失敗時

操作直後に公式クライアントは対象メディアの表示・再生を止め、P2P接続を閉じる。画面は次を分ける。

| 状態 | 表示案 | 処理 |
| --- | --- | --- |
| 保存要求中 | ブロックを保存しています | 操作IDを保持して送信 |
| 正本保存済み・他の接点へ同期中 | 設定を保存しました。各モードに反映しています | 永続的な再試行対象をサーバーにも保存 |
| 接触制限反映済み | ブロックしました | 現在の版と反映済み版を確認して完了 |
| 保存未確認 | 退出しました。ブロックの保存を確認できません。再試行してください | 同じ操作IDで状態照会・再送 |
| 制限反映済み・市場の精算待ち | ブロックしました。預かり金を精算しています | 接触停止と精算の進捗を分ける |

自分の端末で対象を避ける状態を保ちながら再試行する。サーバー保存が未確認であることは隠さない。同じUIDの別端末への反映はサーバーで確認する。アカウント切替時は前UIDの未完了操作・キャッシュ・非同期応答を新UIDへ適用しない。

## 5. 進行中の対戦・商談

### 対戦と自由卓

- ブロック時は相手との接触を終了する。相手側には既存の中立的な終了案内を使い、ブロックという理由を渡さない。
- 未確定の対戦は既存の退出・ノーコンテスト規則に従う。ブロックを新しい敗北免除機能にしない。
- 最終採点等が揃って確定条件を満たした試合は、切断してもサーバーで確定を続ける。ユーザーの読取権限を止めても、採点・結果申告・台帳等の根拠を先に消さない。
- 縁側、品評会、同席中の画像交換も止める。ブロック解除で同じ交流を再開しない。
- 同じ相手との複数モード・複数端末の接点を対象とする。他の相手C/Dとの待機・部屋・商談を巻き込まない。

### 市場の預かり金

全モード共通の終了関数から、対象ルーム・ブロックしたUID・操作ID・ルーム世代を渡して、市場専用の一度だけ実行される精算を呼ぶ。ルームを直接削除しない。

現行の市場キャンセル規則を引き継ぐ案:

- 売り手による終了: 未精算の営業料は買い手へ返す。
- 買い手による終了: 未精算の営業料は既存条件に従い売り手への補償として精算する。
- 延長用の預かり金: 既存条件に従って売り手へ返す。
- 既に成立・精算済み: 再送で状態・残高を変えない。

これはブロック専用の追加ペナルティではなく、現在の終了条件を維持する案である。別モードからブロックされた場合も行為者UIDで売り手/買い手を解決する。両者が同時にブロックした場合は、当該セッションを最初に閉じる共通操作を正本上で一つに確定し、その行為者と閉鎖時状態で精算する。逆順の再送で精算主体を変更しない。

パトロンの既拠出金、会員段階、既成立補助金は取り消さない。新しい相手指定の推薦・優先待機は止める。共通基金からの正当な自動精算は個人間の新規接触として一律拒否しない。

## 6. サーバー構成

### 共通データ（名称は提案）

| 保存先 | 用途・制約 |
| --- | --- |
| Firestore `playerContactPolicies/{pairId}` | 二人のUID、各人のブロック意思、単調増加するペア版番号。実効ブロックは片方でもtrueならtrue。サーバー専用 |
| Firestore `playerSafetyUsers/{uid}/blocks/{opaqueBlockId}` | 本人用管理一覧。相手UIDはサーバー内部のみ。名前の保存時スナップショット等 |
| Firestore `playerSafetyUsers/{uid}/operations/{requestId}` | 本人のblock/unblockの重複防止、要求内容、結果、対象版、反映状況 |
| Firestore `playerSafetyOutbox/{operationId}` | RTDB制限反映、既存接点終了、精算・関係整理の再試行。段階別に完了を保持 |
| Firestoreの非公開context領域 | 確認済みの対戦相手・公開作品の所有者を指す短期ランダム参照 |
| RTDB `online/contactGates/{pairId}` | 正本からの版付き接触制限と、二人に限定した短期接触許可。クライアント直接読書き禁止 |
| RTDBの本人用セッション制御領域 | 対象セッションが終了した事実を通知する。ブロックした側・理由・一覧は含めない |

ブロックの正本はFirestoreへ一本化する。RTDBは権限制御のための投影であり、別のユーザー設定を持たせない。全員のブロック一覧やUID配列をブラウザへ配布しない。

ブロック中の正本にはTTLを設定しない。解除後も、版番号・移行済み印等の最小限の記録を保持し、古い処理による復活を防ぐ。短期context、完了済み操作、期限切れ接触許可、清掃済みoutboxは用途別に保存期限を定める。本文・画像・音声・ブロック理由の自由記述は追加保存しない。

### Callable（名称・引数は提案）

`playerSafetyAction`を認証・App Check必須の独立Callableとして設ける。他のCallableのApp Check公開段階を無関係に変更しない。

| action | 主な入力 | 返すもの |
| --- | --- | --- |
| `get_context` | modeとroomId、listingId、presetId、packId、publicEntryId等 | 本人が操作できる対象だけの短期ランダムcontext。所有者UIDは返さない |
| `block` | contextId、requestId、本人の意思の想定版 | 本人用blockId、保存状態、反映状態 |
| `unblock` | 本人用blockId、requestId、本人の意思の想定版 | 自分の解除処理の状態。相手の意思は返さない |
| `list` | opaqueCursor | 本人のブロック一覧と次ページcursor |
| `get_operation` | 本人のrequestId | 保存・反映・必要な精算の状態 |

contextはサーバーが本人の参加履歴や実際の公開対象から作る。roomIdだけを信用せず参加者・世代を検証する。公開棚からはその出品・作品の所有者を解決する。任意UIDの照会APIや表示名検索でブロック対象を作らない。対戦終了後のcontextは短期・件数上限付きとし、全員分の行動履歴を新設しない。期限切れ後も既存の本人用取引記録等から正しく再検証できる場合だけ再発行する。

block/unblockは本人単位のrequestIdで冪等にする。同じIDで異なる要求内容を再送したら拒否する。遅れて到着した古いblockが新しいunblockを上書きしないよう、本人の意思の想定版を検証する。相手側の同時変更は別の意思として保持し、共通のペア版を更新する。

## 7. 同時操作とFirestore/RTDB間の反映

### 購入・差し入れ・コメント

新しい購入、送金、営業行為、関係登録、コメント作成は、各Firestore transactionの中で共通ペア文書を読む。支払判定の直前に別APIで一度確認するだけでは不十分である。

- ブロックの正本更新が先に確定した場合、新規行為は拒否する。
- 購入・送金が先に確定した場合、その一回分の成立結果を保持する。
- 既存の成功操作IDの再送は、本人・引数・取引一致を検証して保存済みの成功結果を返す。ブロック後だからと「未購入」と返さない。
- 全actionを共通middlewareで拒否しない。履歴、成功結果の再取得、精算・返金、支払済み利用の再開/終了、自己削除、通報は用途ごとに許可する。

Firestore transactionは読み取った文書の同時変更に対して再試行される。この仕組みにペア文書を参加させ、ブロックと新規購入の順序を確定する。[Firebase公式: Transactions and batched writes](https://firebase.google.com/docs/firestore/manage-data/transactions)

### リアルタイム接触

Firestoreの更新とRTDBの更新は一つの原子的な操作として扱わない。次の段階を分ける。

1. Firestore transactionで本人の意思・ペア版・操作結果・outboxを保存する。この時点で新しいFirestore上の行為は禁止する。
2. RTDBの対象ペアgateをtransactionで更新する。古い版を適用せず、実効ブロックと版を更新し、旧版の接触許可を失効させる。
3. 対象接点の終了通知・清掃・精算を世代付きで実行する。処理途中で止まってもoutboxから再開する。
4. 現在の正本の意思とRTDB反映版を照合して、接触制限の完了を返す。古い版の完了を現在の成功として扱わない。より新しい本人操作があれば「更新済み」として最新状態を返す。

Firestore保存からRTDB制限反映までの間は「反映中」である。この間の全モード即時停止を偽って保証しない。公式クライアントの自分側の切断は先に行う。接触制限の完了は、相手端末からの切断確認や市場の全精算完了を待たせない。

新しい部屋への接触許可は、共通gateのtransactionで登録する。許可は二人のUID、mode、roomId、待機・接続世代、試行ID、ペア版、有効期限に結び付ける。gate未初期化・同期未完了・許可欠落は拒否し、欠落を「ブロックなし」とみなさない。正本を確認して初期化できた場合だけ発行する。

部屋にpairId・許可ID・ペア版を保持し、RTDB Rulesで参加者確認に加え「現在のgateが許可状態で、版と当該許可が一致する」ことを読む/シグナル送信/チャット書込の条件にする。状態activeへのAdmin SDK書込そのものをユーザーの接触許可とは扱わない。期限付きの開始許可から、同じセッションと版に束縛された有効な参加許可へ遷移させる。開始許可の期限切れだけで正常な長時間対戦を切断しない。

これにより、ブロック直前に始まった遅い部屋作成が、ブロック後にRTDBへ到着しても接触権限を得られない。解除後も旧版の部屋・許可を復活させず、新たな待機世代と明示的な新規試行を必要とする。古い清掃が、解除後の新しい部屋を終了させないよう、終了処理も同じ世代で照合する。

同じペアのgateだけをtransaction対象とし、全プレイヤーを一つのロックへ集めない。既存マッチングの二重成立防止、セッション所有権、lease、取消、切断復帰の仕組みは維持して、共通許可を追加条件にする。

### 古い入口の閉鎖

- 戦略型の新規部屋作成・招待承諾をサーバーの許可経路へ移す。現在のブラウザだけの候補選定・部屋作成では共通保証を満たせない。
- 通常型V2は既存招待の再取得、承諾、最終部屋作成、接続復帰にも共通許可を適用する。候補除外だけで完成としない。
- コメントはサーバーが所有者を解決するCallableへ移し、ペア判定と同じFirestore transactionで正本を作成する。既存コメントは移行し、旧RTDB直接投稿/更新を閉じる。削除は新Callableで既存権限を保持する。
- コメント本文の旧公開直読も閉じ、閲覧者別の取得へ移す。公開ランキングの数値は維持する。
- RTDB Rulesの親階層に無条件の許可を残したまま、子階層だけへブロック条件を足さない。Rulesは一覧からの自動フィルターにもならない。[Firebase公式: Rulesの継承とフィルターの制約](https://firebase.google.com/docs/database/security/core-syntax)

このgate構成は設計案であり、既存Rules・部屋スキーマへの統合はEmulatorで検証してから確定する。WebRTC通信本体はRTDBを通らないため、公式クライアントの終了処理・受信破棄も必須とする。

## 8. 既存ブロックと関連機能の移行

引継ぎ対象は、現在有効な次のサーバー上のブロック。相手のUID、どちらが登録したかを保持して和集合にする。

- 通常型: `soloFamiliarBlocks` / `soloFamiliarBlockPairs`
- 自由卓: `freeTableBlocks` / `freeTableBlockPairs`
- 推し値市場: `valueMarketShopBlocks/{uid}/users/{targetUid}`

新機能の仕様案として、既存ブロックも全モードへ適用範囲を広げる。公開時に本人へ一度「これまでのブロックを全モード共通に引き継ぎました」と案内し、管理一覧へ進めるようにする。相手には通知しない。この拡張と案内は本書の提案であり、本番への適用はしていない。

推しカードの端末内ミュートは移行しない。表示だけを隠す意思と、全モードで接触を拒否する意思を同一視しない。必要なら本人が別途共通ブロックを選ぶ。

移行手順:

1. 共通正本と移行ID・方向ごとの移行済み印を準備する。旧データはまだ削除しない。
2. 既存block/unblock APIを移行対応にし、移行中の変更を取りこぼさない。旧データだけを書き換える抜け道を閉じる。
3. 既存の有効方向をページ単位で取り込み、旧側の更新と競合した場合は再読込して同じ結果へ収束させる。重複方向は一件にまとめる。
4. 移行後は共通正本を唯一の判定元とする。旧データとの単純なOR読みを永続化しない。そうすると共通側で解除しても旧記録から復活してしまう。
5. 共通側で解除した方向には版と移行済み印を残す。古い移行job・遅延block再送・旧ミラーが再登録しないようにする。
6. 旧画面のブロック/解除操作が共通の範囲を正しく説明できない場合は、明確な更新要求で新画面へ誘導する。黙って無視したり、古い解除操作で別の意味の設定を消したりしない。
7. 顔なじみ、常連、縁、しおり、指定待機・推薦は、相手への新しい接触に使えない状態にする。履歴や売上を消さない。解除時の自動復活はしない。

関係の後処理にも世代確認を適用する。各関係に登録/再同意の世代と当時のペア版を持たせ、旧データは移行時に基準世代を補完する。outboxは元のブロック版と対象関係の世代を照合し、ブロック境界以前に存在した関係だけを無効化・削除する。解除後に本人が明示的に作り直した顔なじみ・常連・しおり・推薦等を、古いブロックの遅延jobで消さない。関係の新規作成も共通ペア文書を同じtransactionで確認する。

移行件数はモード別・方向別・重複除去後で照合する。監査ログに公開名や全UID一覧を出さず、必要な集計とサーバー内部の追跡IDに限定する。

## 9. 所有者マッピング・表示の実装注意

- ランキング公開ID、推しカードID、店コード、出品ID、台本ID、パックIDから、サーバーで所有者を解決する。
- 新しい公開物は、公開応答にUIDを含めず、非公開の所有者対応を作る。
- 断惑NOTEの公開ランキングは現在の公開レコードに所有者UIDがない。非公開マッピングと既存データ補完が必要。表示名一致による推測は禁止。
- 所有者を解決できない公開項目は、補完されるまで接触ボタンや自由記述を控える。正本順位・本人の履歴を捏造・削除しない。
- 一覧・追加ページ・検索結果・推薦棚・直接ID照会で同じ判定を使う。本人向け応答は他UIDと共有キャッシュしない。
- 非表示項目が続くページでも同じcursorへ戻らない。走査上限と次のcursorを返し、必要なら「さらに読み込む」を出す。ブロック相手の人数や名前は返さない。
- ブロック前に開始した非同期読込が後から到着して画面へ相手を復活させないよう、本人UIDと設定世代が古い応答を破棄する。

## 10. 通信量・運用

- ブロック一覧は開いた時・変更時に取得し、ページ送りする。全員のブロック関係を常時購読しない。
- 同じUIDの別タブ/別端末には、本人用の設定版だけを小さく通知し、必要な表示を再取得する。対戦中の終了制御は既存の対象セッション購読へ統合する。
- 候補選びでは対象候補分のペアをまとめて取得し、ページ/候補数の上限を維持する。除外されたA/BのためにA/CやC/Dまで待ち続ける選定にしない。
- 候補選びのキャッシュは事前絞り込みにだけ使用する。最終課金・投稿・接触許可を古い「ブロックなし」で通さない。
- 権限判定に失敗した接点は成立を保留して再試行する。一人用プレイ、本人の履歴、返金・精算までまとめて止めない。
- 候補のペア読込、成立時の許可登録、RTDB購読、outbox清掃を別々に計測する。「Callableが一つ増えるだけ」と費用を見積もらない。
- outboxは再試行間隔を広げ、処理上限・試行数・失効許可の清掃を持たせる。同期失敗を理由にブロック設定を消さない。
- ブロック件数に小さな上限を設けて古い設定を自動解除しない。大量操作対策は操作頻度・正当な対象context・ページ取得上限で行う。容量上限が必要になった場合も保存失敗を明示する。

## 11. 公開順序と戻し方

全モード共通の表示を出すのは、全接点で強制できた後とする。開発は分割しても、1on1だけ対応した時点で「全モード共通」と公開しない。

1. 共通サービス、正本、App Check設定、必要なインデックス、権限・outbox・移行jobを実装して検証。
2. 通常型/戦略型/自由卓/市場の接触経路と、購入/差し入れ/コメント等を接続。所有者の非公開マッピングを補完。
3. 既存ブロック移行と旧更新API対応を行い、差分を照合。
4. 新しいプロトコルに対応するFunctionsとRulesを先に配備。移行中の既存対戦・商談は履歴と精算を保護し、未対応の新規入口を段階的に閉じる。
5. 新しい画面を配備し、対応済みでない古いクライアントには更新を要求。既存アクティブ部屋も移行または終了を確認し、無期限の旧権限例外を残さない。
6. 全接点の強制を2～3アカウントと旧クライアントで検証してから共通入口と引継ぎ案内を公開。
7. Firebase Hostingの両ドメインとWorkerで、配信コード・キャッシュキー・Rules/Functionsとの組合せを別々に確認。

障害時に旧マッチャーへ戻してブロックを無効化しない。表示を戻す場合も共通のサーバー判定は残す。必要なら影響するモードの新規接触だけを一時停止し、進行済み取引の精算と本人データの利用を維持する。

本書は公開対象から除外済みの`functions/`配下に置く。既存のHosting/Worker公開設定を変更せず、設計書が公開アセットに混入しない位置を使用している。

## 12. 受入条件

### 共通・対象識別

- AがBを一つのモードでブロックすると、他の全接点でも新規交流を拒否する。A/C、B/Dは継続できる。
- Aだけの解除では、B側の意思が残る限り対戦・交流・取引できない。
- 名前変更、公開カードの再作成、同じUIDの別端末でも適用する。別UIDを名前で誤ブロックしない。
- 偽roomId・他人のcontext・期限切れcontext・他人のblockId・自己ブロックを拒否する。
- 未公開の顔なじみ帳、未参加のランキング、AnjuPay残高ゼロでも共通機能を使える。

### 並行操作・復旧

- 候補選定直後、招待作成直後、承諾直前、部屋保存直後、接続復帰時の各タイミングでblockを挿入し、反映完了後に旧許可で接触できない。
- ブロック後の解除でも、古い招待・遅延job・旧接続世代が復活しない。
- Firestore保存後/RTDB反映前/反映後応答前で障害を起こし、正しい「反映中」「完了」を返す。
- block→unblock後に元のblockを再送しても上書きしない。双方の同時操作・同名重複・ページ送りも検証。
- 同じUIDの別タブで変更し、古い画面の候補・相手情報・未送信操作が復活しない。
- 親階層のRules、旧直接コメント書込、古い戦略型の部屋作成、直接招待URL、直接商品IDで迂回できない。

### 戦績・経済

- 最終採点成立前/成立後の退出境界で、既存の正当な結果だけが一度確定する。
- ブロックと購入の同時実行で、ブロックが先なら新規課金ゼロ、購入が先なら一回分だけ成立し履歴を取得できる。
- 市場の全預かり状態で、売り手/買い手/別モードからの終了、双方同時block、精算中障害を検証。正当な残高・予約枠・台帳へ一度だけ収束する。
- 支払済み台本・パックの再開/終了/通報を妨げず、新しい課金は拒否する。
- 差し入れの成功応答を失った後にblockしても、再送で二重送金も「未送信」の誤報もしない。
- 証書・レシート・実績・パトロン拠出金・既成立補助金を消さない。

### 非公開性・移行

- 管理一覧は本人が登録した相手だけ。相手側のフラグ、UID、理由、被ブロック件数を公開応答へ含めない。
- 既存コメントは本人向けに隠れ、投稿者/欄の持ち主は削除できる。ランキングの順位・母集団は変わらない。
- 既存3系統のブロックを方向付きで引き継ぎ、旧データから解除済み関係が復活しない。ローカルミュートは変えない。
- block→unblock→新しい関係登録→古い関係整理jobの順でも、解除後に明示的に作り直した関係を消さない。
- 全モードの一覧・追加ページ・推薦・復帰・履歴からの再接触を確認する。
