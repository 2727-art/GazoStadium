# 貼り合いスタジアム

トップページには「10秒音声メーカー」があり、端末のマイク録音または20MB以下の手持ち音声を、戦略型1on1用の先頭10秒・22.05kHz・モノラル・16bit WAVへブラウザ内だけで変換できます。変換後はその場で試聴・保存でき、Firebaseや運営サーバーには送信しません。

好きな画像を用意し、知らない相手と魅力を競うオンライン画像ゲームです。1～10点で戦う1on1・2on2、順位投票で生き残る4人バトルロワイヤル、ゲーム内通貨AnjuPayで推し値を競う「推し値市場 / VALUE MARKET」を遊べます。

- Firebaseで匿名ログイン・対戦相手の検索・対戦同期・チャットを行い、画像本体はWebRTC DataChannelで対戦相手へ直接送信
- トップ画面の「戦略型1on1対戦」から、匿名自己紹介を読んで相手対策デッキを組むオンライン対戦を遊べます
- トップ画面の参加状況は、通常型1on1・戦略型1on1・2on2・バトルロワイヤルを別々に表示します
- トップ画面の参加状況はRealtime Databaseを購読し、待機・対戦状態の変化をリアルタイムで更新します
- オンライン総合ランキングは4モードの結果を合算し、デイリー・ウィークリー・マンスリーの選択中期間だけFirebase SDKで取得します。切替日以降の期間はCloud Functionsが検証済み試合から確定します
- ランキング参加設定は4モード共通で、各モードの準備画面とランキング画面から切り替えられます
- 任意のプロフィール画像を同一ブラウザのIndexedDBへ保存し、対戦中だけWebRTCで参加者へ直接転送します
- ランキングコメントも欄を開いた時だけ取得し、投稿・削除時だけ匿名認証付きFirebase SDKで接続します
- トップページの「みんなの推しカード」へ基本カードを無料公開でき、遊んだ歩みで育つ段階、紹介文、実績、任意のXリンクを作品名刺として表示します
- 推し値市場のAnjuPay残高移動・売買状態・独立ランキングはCloud FunctionsとCloud Firestoreのトランザクションで確定し、画像と10秒音声はWebRTCで相手へ直接送信します
- 市場成約時だけ売り手へ通常5%の手数料を課し、対象取引ではパトロン循環基金から一部を補填します。買い手には画像を含まない非譲渡の「推し値証書」を発行します
- 4つのオンライン対戦を正式完走した後、参加者1人へ5 Pay・10 Pay・20 Payの「差し入れ」を1回だけ送れます
- 匿名データを任意のGoogleアカウントへ連携し、同じUIDのAnjuPay残高・購入品・実績・戦績を別端末から復元できます
- Google保護済みプレイヤーは、毎月300 Pay / 1,500 Pay / 5,000 Payを使うVALUE MARKETパトロンへ昇格できます。支払いの20%は当月の市場循環基金になります

## 起動方法

ES Modulesを使うため、ローカルサーバーから開きます。ビルドやパッケージのインストールは不要です。

```powershell
python -m http.server 4173 --bind 127.0.0.1
```

その後、`http://127.0.0.1:4173/`を開きます。オンライン対戦の動作確認は、1on1なら2環境、2on2・バトルロワイヤルなら4環境のように、保存領域の異なるブラウザまたはブラウザプロファイルで行ってください。

## AnjuPay

AnjuPayは、貼り合いスタジアムのTRPG世界観とゲーム内経済圏を楽しむためのゲーム内通貨です。利用単位は`Pay`で、獲得条件、報酬額、商品価格、残高上限など既存の基本値を維持します。VALUE MARKETパトロン支払いの一部は市場循環基金として対象取引の手数料補填に使い、「残高を増やす」だけでなくAnjuPayを使うことが市場の出会いと再訪を支える設計にします。

- AnjuPayは貼り合いスタジアム内だけで獲得・利用できます。現金チャージ、換金、プレイヤー間の自由送金、ゲーム外での利用には対応せず、将来も追加しません
- 対戦後の差し入れやVALUE MARKETなど、ゲームが用途と相手を限定した既存の移動だけを許可します
- 履歴機能の開始前に起きた増減を完全には復元しません。初回に「AnjuPay開始残高」を1件記録し、それ以後に確定した獲得・利用・市場取引・差し入れをすべて記録します
- AnjuPayの単位表示を`Pay`へ統一しても、残高の数値、商品価格、報酬、購入済み状態、ランキングや採点に使う非通貨スコアの仕様は変わりません

## 対戦ルール

### 推し値市場 / VALUE MARKET

AnjuPayの使い道を広げたいプレイヤー向けに、画像の魅力を営業し、点数ではなくゲーム内通貨で推し値をつける独立エンドコンテンツです。売買はTRPGとしてのロールプレイであり、画像データ・著作権・所有権そのものは移転しません。

- 売り手は画像1枚、出品タイトル、販売価格10～500 Pay、営業方法を登録し、買い手は購入上限を登録してロール別にマッチング
- 画像はマッチ成立後にWebRTC DataChannelで買い手へ直接送信し、FirebaseやCloud Storageには保存しない
- 買い手は画像と販売価格を無料で確認し、「営業を受ける」を選んだ時点で着手料5 Pay分をAnjuPay残高からFunctionsが保留する。売り手がチャットまたは10秒音声を送り営業完了を確定すると売り手へ移り、売り手が完了前に終了した場合は買い手のAnjuPay残高へ返還する
- 無料プレビュー段階を設けることで、売り手がマッチングと即退出を繰り返して着手料だけを得る行為を防ぐ
- 売り手は240文字以内のチャット、またはゲーム用に変換した最大10秒のWAV音声で営業
- 営業終了後、買い手は販売価格で購入、退室、もう1ターン検討から選択
- 接客スタイルに「推し嬢（熱血クロージング）」を掲げた売り手は、各営業ターンの完了時に通常営業を続けるか、推し嬢モードへ切り替えるかを選べる。推し嬢モードでは追加検討を終了し、買い手を「購入」または「見送り」の最終判断へ案内する。この条件は着手料を払う前の無料プレビューで明示する。自動購入や時間切れ購入は行わず、購入代金は買い手が金額・着手料を含む総支出・購入後残高を確認し、最終確認を開いて明示的に購入を確定した場合だけFunctionsが処理する
- 購入成立時だけ販売価格の5%（端数切り上げ・最低1 Pay）を売り手負担の通常手数料として計算する。買い手の支払額は販売価格のまま。パトロン循環基金の対象取引では通常手数料の半分（端数切り捨て）を最大10 Payまで基金から売り手へ補填し、実質手数料を最低1 Pay残す
- 購入成立と同じFirestoreトランザクションで、買い手へ「推し値証書」を1枚発行する。証書は番号、出品タイトル、売り手表示名、推し値商店の来歴、成約価格、通常手数料、基金補填、営業ターン、成立日時を持つ非譲渡コレクションで、補填された証書には`PATRON BACKED`を表示する。画像・音声・チャット・著作権・所有権は含まない
- 追加検討では、売り手が5 Pay・10 Pay・20 Payの内金を提示した時点でAnjuPay残高からFunctionsが保留し、買い手が受け取った場合だけ買い手へ移して次の営業ターンへ進む。辞退・取引中止時は売り手のAnjuPay残高へ返還する
- 営業は最大3ターン。着手料、内金、購入代金に伴うAnjuPay移動はすべてCloud Functionsだけが確定し、保留中は受取候補双方の残高上限枠も予約する
- 売買成立時だけ売り手の売上・成約数と買い手の購入額・購入数を更新し、総合ランキングとは別の市場ランキングへ集計
- トップページの「推し値市場ランキング」から市場準備画面を経由せず、既存の売り手・買い手ランキングへ直接移動。トップページから開いた場合は「タイトルへ戻る」で元の画面へ戻る
- 同一の売り手・買い手ペアは日本時間の1日につき最初の成立取引だけをランキングへ加算し、相互売買による順位水増しを抑制
- 市場ランキングへ、本人が明示的に公開したXユーザー名と1行40文字以内の「市場プロフィールの一言」を任意表示。Xは自己申告として表示し、自由入力URLではなく検証済みユーザー名から`x.com`リンクを生成する
- 画像の一時判定や音声通報機能は設けず、既存方針どおりユーザー自治で遊ぶ

#### 推し値商店と「誰から買うか」

推し値市場では、出品画像だけでなく「誰がどんな基準で選び、どう魅力を伝えるか」を継続して楽しめるよう、売り手ごとの推し値商店を持てます。

- **推し値商店**: 売り手は16文字以内の店名、40文字以内の短い紹介、得意分野、接客スタイル、店テーマを設定し、出品ごとに同じ店主として営業できます。接客スタイルの「推し嬢（熱血クロージング）」は、情に厚い熱血店主として買い手の迷いと向き合い、営業完了時に最終判断へ導けることを無料プレビュー中から予告します。店名と紹介は1行に正規化し、URLや制御文字を拒否します。初出品の店には新人表示を付け、実績が少ないことを低評価として扱いません。
- **店コード**: Functionsが匿名UIDをそのまま公開しない店コードを発行します。表示名を変えても商店を見分けるためのゲーム内識別子で、Firebase AuthenticationのUIDやGoogleアカウント情報ではありません。
- **商印**: 売り手が選んだ商印を店主カード、営業、証書来歴へ共通表示し、所有する称号や店テーマと組み合わせて接客の個性を作れます。
- **商店チャーム**: 無料4種とAnjuPayストアで購入済みのスタンプから1個を選び、店主カード、常連帳、営業、証書来歴へ店の目印として表示できます。チャット用の最大6個の装備枠とは独立して選択し、サーバーは無料または本人が所有するスタンプIDだけを保存します。商印・称号・チャームなどの装飾は品質保証やAnjuPay上の有利不利を表しません。
- **店主カード**: 買い手は無料プレビュー中に、店名、店コード、商印、商店チャーム、紹介、得意分野、検証済みの市場実績を画像と一緒に確認します。任意公開のXリンクは自動的に店主カードへ転載しません。
- **常連帳**: 買い手は営業完了まで接客を受けた商店を、自分だけの常連帳へ100店まで追加・解除できます。店コードだけを知っている未接客の商店は追加できません。誰が登録したかは売り手へ伝えず、店主本人の非公開レポートに合計人数だけを表示します。公開店主カードには合計人数も表示しません。
- **優先待機**: 買い手が常連帳で「この商店を待つ」を選び、その売り手も「常連歓迎」を有効にしている場合だけ、選択した1店に限定して待機します。出品価格が購入上限以内で、買い手のAnjuPay残高が販売価格と着手料5 Payの合計以上ある商談だけ成立します。条件が合わない間は選んだ商店を待ち続け、買い手自身で一般市場へ戻せます。
- **肯定タグ**: 営業完了まで接客を受けた買い手だけが「やさしい接客」「新しい魅力に気づけた」「言葉・声が印象的」「もっと見たい」から1つ返せます。購入をタグ送信の条件にはせず、自由記述や星評価、低評価も設けません。同じ売り手・買い手からの集計は30日に1回までとし、短期間の繰り返し商談で商店評価を増やせないようにします。異なる買い手5人に届くまではタグ別件数を公開せず、収集中として表示します。
- **ブロック**: 同じ商談へ参加した相手を結果画面でブロックすると常連帳から外れ、以後の一般待機と優先待機の候補から相互に除外します。誤操作した場合は同じ結果画面にいる間ならすぐ解除できます。ブロックや解除の理由は相手へ公開しません。
- **証書来歴**: 成約時点の店コード、店名、商印、商店チャームなどの公開商店情報を証書へ記録します。後から店名やテーマが変わっても「どの店主から買ったか」を確認できますが、元画像や営業本文は保存しません。

#### パトロン推薦棚

パトロンはAnjuPayを追加で支払わず、接客済みまたは常連帳へ登録した推し値商店を推薦できます。推薦は売り手への直接送金や品質保証ではなく、「誰から買うか」の発見を助ける市場内キュレーションです。

- `SUPPORTER / PATRON / GRAND PATRON`は当月それぞれ1店 / 2店 / 3店まで推薦でき、推薦枠の購入や推薦に応じたAnjuPay報酬は設けない
- 同じ商店への推薦は1人1件だけとし、解除して別の商店へ枠を使える。自分自身の商店は推薦できない
- 同じ月に異なるパトロン3人以上から推薦された商店だけを「パトロン推薦棚」へ掲載する
- 推薦棚は店コードと公開用の商店情報だけを返し、売り手・推薦者のFirebase Authentication UIDやGoogleアカウント情報を公開しない
- 買い手は推薦棚から1店を選び、待機開始後20秒だけその商店を優先して探せる。見つからない場合は一般の新規商店検索へ自動で広がり、少人数時も待機を固定しない
- 推薦数の多さ自体は検索順、成約価格、市場ランキング、AnjuPay獲得量を上乗せしない。閉店などでカードを表示できない推薦も、本人が折りたたみ管理欄から解除して枠を空けられる

市場の待機列、アクティブルーム、取引状態、AnjuPay残高、移動台帳、ロール別実績、推し値商店の正本・公開用スナップショット、常連帳、ブロック関係、売り手・買い手ペア、肯定タグの重複防止台帳、証書メタデータ、パトロン循環基金・補填台帳・月間方針投票・推薦枠はCloud Firestoreに保存します。これらはFirestore Rulesでクライアントの直接読み書きを拒否し、本人認証済みCallable Functionsが用途ごとに必要な公開情報だけを返します。証書コレクションは最新100件まで取得します。市場公開プロフィールは売上または購入実績がある本人だけがCallable Functions経由で更新でき、クライアントから統計ドキュメントへ直接アクセスできません。チャット、WebRTCシグナリング、接続状態だけを参加者限定のRealtime Databaseルームへ保存し、画像・音声本体はP2Pメモリ内だけで扱います。

評価悪用対策として、肯定タグと常連帳追加はFunctionsが営業完了済み商談の買い手本人かを確認します。肯定タグは商談単位の冪等キーと売り手・買い手ペアの30日間隔で、再送・短期連投による単純な重複加算を防ぎます。常連帳は同じ商店への登録を1件だけ保持し、追加と解除を繰り返しても公開実績へ加算しません。既存の同一ペア日次ランキング除外、App Check、商談台帳も併用します。ただし、商店の実績や肯定タグはプレイヤーの主観的な「選び方・伝え方」の手掛かりであり、画像の客観的品質、安全性、権利関係を保証するものではありません。複数アカウントによる組織的な評価操作を完全には識別できないため、Functionsログと商店ごとの急増を継続して監視します。

### 対戦後の差し入れ

通常型1on1、戦略型1on1、2on2、4人バトルロワイヤルの最終結果画面では、その試合の自分以外の参加者1人へ5 Pay・10 Pay・20 Payから選んで差し入れできます。

- AnjuPayを新規発行せず、送信者のFirestoreウォレットから受取人のウォレットへそのまま移すため、全体のAnjuPay総量は増えない
- 送信者1人につき1試合1回だけ。送信後の取消、受取人変更、追加送信は不可
- 自分自身、試合に参加していないUID、ノーコンテスト、全員の結果が揃っていない試合、検証済み試合台帳がない試合はFunctionsが拒否
- 最終結果画面は検証済み試合台帳を確認するまで送信操作を無効化し、相手の確定が遅れた場合は「対戦記録を再確認」から再照会できる
- 数量はFunctions側の固定表だけを許可し、AnjuPay残高不足または受取人の残高上限到達時は両者の残高を変更しない
- 勝敗、RATE、ランキング、実績、ミッション進捗には影響しない

### データ保護・別端末復元・VALUE MARKETパトロン

トップ画面の「AnjuPayウォレット」から、現在の匿名データを任意のGoogleアカウントへ連携できます。連携時は新しいゲームデータを作ったり残高を複製したりせず、現在のFirebase Authentication UIDをそのまま維持します。別端末の「別端末のGoogleデータを復元」は、まず現在のゲストUIDへのGoogle連携を試し、すでに保護済みデータがある場合だけ確認後にそのUIDへ切り替えます。選択したGoogleに既存データがなければ空の新規UIDへ移らず、現在のゲストデータをそのまま保護します。端末側とGoogle側のAnjuPay残高は合算しません。

- Google保護で復元される対象は、UIDに保存されたAnjuPay残高、購入品と装備、ミッション・期間報酬、実績、オンライン戦績、市場実績、推し値証書、差し入れ送信台帳、パトロン履歴、当月の推薦枠と方針投票
- プロフィール画像、選択した対戦画像・音声、戦略型プロフィール、SE設定などブラウザ内だけに保存するデータは別端末へ復元しない
- 高額支払いはGoogle保護済みアカウントだけが実行可能。日本時間の月ごとに`SUPPORTER 300 Pay / PATRON 1,500 Pay / GRAND PATRON 5,000 Pay`の3段階を用意し、上位へは差額だけを支払う
- パトロンは市場ウォレットと商談相手へ表示する名誉バッジに加え、循環基金、非課金の商店推薦、月間方針投票へ参加できる。採点、マッチング、勝敗、市場ランキングを直接優遇しない
- 昇格価格はクライアント入力を信用せずFunctions側の固定表から算出し、Firestoreトランザクションと操作IDで二重支払いを防止
- 商談・対戦・待機中は、AnjuPay残高の競合を避けるためパトロン昇格とアカウント引き継ぎを拒否

#### パトロン循環基金と月間方針

- パトロン昇格で支払ったAnjuPayは、同じFirestoreトランザクションで80%を消却し、20%を日本時間の当月だけ使う循環基金へ積み立てる。上位昇格の差額支払いも同じ比率で分ける
- 補填はApp Check確認済みの売り手・買い手で成立した商談だけが対象。通常5%手数料の半分（端数切り捨て）を最大10 Payまで基金から売り手へ加算し、実質手数料を最低1 Pay残したうえで基金残高を超えて補填しない
- 対象関係は「その売り手と買い手の初成約」または「前回と別日の再成約」。同じ売り手・買い手ペアへの補填は月1回まで、同じ売り手への補填は月合計50 Payまでとし、当日中の反復や少数ペアによる基金の集中消費を防ぐ
- 当月パトロンは`出会いと常連 / 新しい出会い / 常連の信頼`へ1票を持つ。出会いと常連は初成約と別日再成約、新しい出会いは初成約、常連の信頼は別日再成約だけを対象にし、現在の集計結果を当月の有効方針として表示する
- AnjuPayウォレットの`Impact`には本人が基金へ回した額、推薦枠と推薦数を表示し、市場には基金総額、補填済み額、残額、支援成約数、消却額を表示する。補填された結果画面と推し値証書には`PATRON BACKED`を表示する
- 基金は成約手数料の補填だけに使用し、パトロン本人や買い手への直接付与、購入代金の返金、自由送金には使わない。基金残高不足、上限到達、条件不一致時は通常の5%手数料で安全に成約を続行する

Googleを利用できない場合だけ、補助手段として16文字の使い捨て引き継ぎコードを発行できます。コードは10分で期限切れとなり、新しく発行すると以前のコードは無効になります。復元先は対戦、購入、AnjuPay獲得などをまだ行っていない新しい匿名アカウントに限定し、データをコピーせず発行元と同じUIDへログインします。Google保護後はコードを発行できません。コードはFirestoreへ平文保存せずSHA-256ハッシュだけを保存し、連続試行制限、App Check強制、トークン再利用防止を常時適用します。コードを知った第三者は期限内ならデータへアクセスできるため、SNSやチャットでは共有しないでください。復元後も発行元端末は自動ログアウトされません。

### 戦略型1on1対戦（オンライン）

Firebaseの専用待機キューで採点傾向が近い相手を優先してマッチングし、匿名自己紹介から相手の好みを推測してデッキを構築する2人用オンラインモードです。

- 各プレイヤーは名前、弱点候補3つ、追撃セリフを先に登録し、本当の弱点1つとブラフ2つを決める
- 「アニメ・イラスト」「実写」「どちらも歓迎」から高く評価しやすい画像表現を自己申告する。画像の内容をゲームが自動判定するものではない
- 同じ採点傾向を最優先し、「どちらも歓迎」を次に優先する。異なる傾向同士は待機20秒後に両者が「条件を広げて探す」を選んだ場合だけ成立する
- 追撃セリフは定型文または自由記述を選択。自由記述は1行・最大40文字で、空白時は定型文へ戻る
- 弱点は乱数付きSHA-256コミットとして先に共有し、回答確定後の公開時に改変されていないことを照合
- マッチ成立後は相手の名前を伏せたまま3つの弱点候補を表示し、対戦を受けるか撤退するかを選択
- 匿名紹介からデッキ封印までは名前・プロフィール画像・チャット装飾を伏せた専用チャットで質問やブラフを交わし、弱点推理の材料にできる
- 対戦を受けたプレイヤーは、メイン5枚と任意のリザーブ最大5枚を相手の好みに合わせて構築
- 各画像には任意で音声を1つ添付可能。ブラウザ内で先頭10秒までを22.05kHz・モノラル・16bit WAVへ変換し、音量を正規化する
- 追撃用に音声内の3秒区間を指定でき、弱点看破後の連続追撃では最大3枚・合計最大9秒を順番に再生
- 両者のデッキ封印後にプレイヤーネームを公開
- 名前公開後も全対戦フェイズでチャットを継続し、参加者欄と発言横にP2P受信済みのプロフィール画像を表示
- 最大5ラウンド。両者がメイン画像を秘密選択し、同時公開後に相手の画像を1～10点で秘密採点
- 採点とは別に、各プレイヤーは1～3点時の「もう1枚見せろ」を2回、9～10点時の「追撃を許可」を1回まで使用可能
- 追加要求を受けた側はリザーブを1枚提示し、メインと追加画像の高い方をラウンドの画像パワーに採用
- 追撃側は事前登録セリフとリザーブを公開し、追撃画像の採点の半分をメインの画像パワーへ加算
- 追加画像から追加要求・追撃は連鎖せず、両者の画像パワー確定後に高い側が同値のダメージを与える
- 各ラウンドの結果後、どちらかが一度だけ早期看破を宣言可能。宣言すると両者の秘密回答フェイズが始まり、未宣言ならROUND 3後に強制開始
- 両者の回答確定後に弱点を公開してコミットを検証。看破失敗者は自分に5ダメージを受け、再回答できない
- 看破成功者は残っているリザーブから最大3枚を選び、`4 → 3 → 2`の固定ダメージで連続追撃。両者成功時は同時解決
- 弱点を看破された側は連続追撃結果で「参りました」を選択でき、HP0のSURRENDER KOとして決着する
- 連続追撃でHPを超過したダメージは`OVERKILL`として演出し、ランキングスコアやRATEへは加算しない
- 連続追撃後にHP0なら決着し、それ以外は最大5ラウンドまで継続。同HPなら連続追撃を含む累計画像パワーで判定
- 試合後に両者の本当の弱点・ブラフ・弱点回答・各ラウンドの画像パワー・平均評価を表示
- 対戦中は最大10秒・480p・約2MBの短尺映像を1本録画し、内容を確認してから相手へP2Pで一時送信できる。リアルタイム映像配信とファイルアップロードは行わない
- 試合後は両者が参加を選んだ場合だけ最大10分の品評会を開く。対戦で使用した画像を端末内データから再送なしで見返せるほか、1人につき追加画像3枚、10秒音声1本、品評会用短尺映像1本をP2Pで共有できる。片方の辞退・退出・切断・時間切れで終了する
- 品評会の追加画像は最大1280pxのWebP・約1.5MB以下へ再生成し、音声ファイルまたはマイク録音は最大10秒・22.05kHz・モノラル16bit WAV・約480KB以下へ変換する。送信前に本人がプレビューし、受信側では自動再生せず、途中でメディア受信を停止したり個別に端末から削除したりできる

自己紹介、受諾・撤退、デッキ準備、専用チャット、秘密採点、ラウンド進行、品評会への同意と終了状態は参加者だけが読めるRealtime Databaseルームで同期します。チャットは匿名紹介から利用でき、デッキ封印までは相手名・プロフィール画像を表示しません。対戦画像と添付音声は既存のWebRTC DataChannel、短尺映像と品評会の追加画像・音声は同じPeerConnection内で用途別に分離した専用DataChannelから対戦相手へ直接転送します。画像・音声・映像本体はFirebaseやCloud Storageへ保存せず、対戦・品評会の終了またはページ終了時にObject URL、Blob、カメラ・マイク参照を解放します。

### 1on1

- 対戦前に各プレイヤーが画像を5枚選択
- 通常型では「アニメ・イラストが刺さりやすい」「実写が刺さりやすい」「どちらも歓迎」から、自分が高く評価しやすい画像傾向を自己申告
- 同じ傾向同士を最優先し、「どちらも歓迎」は両方の傾向とマッチング。異なる傾向同士は待機20秒後に両者が「条件を広げて探す」を選んだ場合だけ候補にする
- 画像の内容は自動判定せず、選択した傾向はマッチング条件だけに使用して対戦画面には表示しない
- 最大HPは30、最大5ラウンド。サンプル画像を含む場合は1枚につき最大HPが5減り、5枚すべてサンプルならHP5で開始
- 各ラウンドで未使用画像を1枚ずつ秘密裏に選択
- 両者の通信準備完了後に10秒の選択タイマーを開始し、時間切れ時は選択中または未使用の画像を自動ロック
- 両者の選択完了後に画像を交換・公開
- 通常型は気軽に交流できるフリーモードとして、対戦ルーム成立後から試合終了までチャットを常時利用可能
- 相手の画像を1～10点で採点
- 高得点側が勝利し、低得点側は高得点と同じ値のダメージを受ける
- 同点ラウンドは両者ノーダメージ
- 8～9点は `CRITICAL!`、10点は `PERFECT!!`
- 9～10点を受けた画像の持ち主について、事前登録した追撃セリフをラウンド結果へ表示（オンライン1on1では演出のみ）
- 通常型1on1では、ダメージで相手HPを正の値から0にした実際の画像を使って `FINISH` カットインを表示。デッキから任意の1枚をシグネチャーカードに指定し、そのカードで決着した場合は `SIGNATURE FINISH` の強化演出になる
- フィニッシュセリフは定型文・1行30文字までの自由記述・セリフなしから選択可能。受け手は相手の自由記述だけを非表示にし、安全な定型文へ置き換えられる
- 通常型1on1の準備画面では、王道主人公・好敵手・騎士／武人・魔王／悪役・無口／クール・コミカル・推し活の口調セットから、追撃・決着・敗北時の返礼を一括設定できる。セット適用後も各セリフを個別に定型文・自由記述へ変更可能
- HPを0にされた側には、登録済みの決着返礼を確認して自分で応えるボタンを表示する。返礼は最大40文字・改行1回までの自由記述、定型文、返礼なしから選択でき、応答後は勝者の決着口上と並べて両者に表示する
- 決着返礼は勝敗確定や戦績保存を待たせない任意演出で、未操作・スキップ・切断時は拒否扱いを表示せず一定時間後に結果へ進む。AnjuPay・実績・ミッション報酬は付与しない
- HPが0になると敗北
- 5ラウンド終了時は、残りHP、合計獲得点、CRITICAL回数、10点回数の順で判定
- すべて同じ場合は引き分け
- 試合後の「縁側で一息」は、両者が参加を選んだ時だけ開く通常型1on1専用の任意交流。手元の画像1枚と固定の気分札をP2Pで見せ合い、採点・HP・戦績・AnjuPay・ミッション・実績に影響しない固定のひとことを1回だけ返せます。片方の辞退・退出・切断で閉じ、同意・画像・気分・反応はFirebaseへ保存しません
- 顔なじみ帳は「縁側で一息」で双方の画像が端末間に届いた後にだけ表示する任意機能です。各自が「またどこかで」を選んだ場合だけ、Cloud Functionsが12時間以内の完走済み通常型1on1と両者の検証済み結果申告を確認して関係を作ります。片方だけの希望と「この場だけ」は相手へ通知せず、「この場だけ」はサーバーへ送信しません
- 顔なじみ帳に表示するのは対戦時の名前だけで、オンライン状態・最終ログイン・勝敗・回数・画像・気分・ひとことは表示しません。1人最大100件です。帳面から外すと双方から静かに消え、ブロックすると顔なじみ関係と再会優先から外れます。通常検索で偶然同じ相手になることまで保証して防ぐ機能ではありません
- 再会マッチングは通常型1on1の待機列を分けず、双方が端末で希望し、同時に待機中で、直近24時間に再会優先が成立していない顔なじみを先に探します。該当者がいなければ待ち時間を延ばさず、その場で通常の相手へ戻ります。専用報酬・連続ログイン・回数ノルマ・相手のオンライン通知はありません
- ルーム破棄は勝敗・勝率・連勝数に影響しない

### 2on2

- 待機中の4人が揃うと、ランダムに2人ずつのTEAM A / TEAM Bへ自動分配
- 各プレイヤーが画像を5枚選び、最大5ラウンドすべてで4人全員が1枚ずつ提出
- 各ラウンドは20秒のチーム専用作戦チャットと `TEAM LINK` 作戦選択後、10秒の秘密選択を実施
- 相方と同じ作戦を選ぶと `TEAM LINK` 候補になり、2枚の画像得点が条件を満たすと発動
- `シンクロ` は2枚とも平均7点以上で勝利時+2ダメージ、`エース支援` は片方9点以上・もう片方5点以上で勝利時+3ダメージ、`カバー` は2枚とも平均6点以上で敗北時-2ダメージ
- 選択時間切れ時は、選択中または未使用の画像を自動ロック
- 4枚の公開後、各プレイヤーが相手チームの2枚を別々に採点
- 採点時間は20秒。時間切れ時の未採点画像は5点として自動確定
- 画像得点は相手チーム2人の採点平均、チーム得点はチーム2枚の画像得点平均
- 高得点チームが勝利し、四捨五入したチーム得点へTEAM LINKの追加攻撃・軽減を反映して相手の共有HP30へダメージ
- 画像得点の平均が8点以上で `CRITICAL!`、相手2人がともに10点なら `PERFECT!!`
- 5ラウンド終了時は、共有HP、累計チーム得点、TEAM LINK発動数、CRITICAL数、PERFECT数の順で判定
- 作戦中は同じチームの2人だけが読めるチャット、画像公開後は4人共通チャットを使用
- ルーム破棄・切断はノーコンテストとなり、2on2戦績とミッションには影響しない

### 4人バトルロワイヤル

- 待機中の4人が揃うと自動的に個人戦を開始
- 各プレイヤーは `OPENING`・`MIDDLE`・`FINAL` のメイン3枚とリザーブ2枚を登録
- 1試合に1回だけ、そのラウンドのメイン画像を未使用リザーブへ交換可能
- 画像選択は10秒、順位投票は15秒。時間切れ時は選択中の画像・未選択順位を自動ロック
- 画像の持ち主は投票確定まで非表示で、選択・公開・投票中は4人チャットを停止
- 4人生存時は他の3枚を1位3点・2位2点・3位1点、3人生存時は他の2枚を1位2点・2位1点で順位投票
- 毎ラウンド最下位の1人が脱落し、4人→3人→2人→優勝者の順で決着
- 最下位同点の場合は対象者だけがリザーブ画像を提出するサドンデスを実施
- FINALは脱落した2人が優勝画像へ投票。同票なら過去ラウンドの支持率・1位票・ラウンド首位回数・ルーム単位の決定的抽選で判定
- 脱落者はFINAL前まで勝敗に影響しない観客賞を選び、投票確定後の4人共通チャットにも参加
- 結果画面は8秒後に自動進行し、一時切断は30秒間の再接続猶予後に本人だけを失格として対戦を継続
- バトルロワイヤル専用戦績として優勝回数、TOP2回数、対戦数、現在・最高連勝を保存

## オンライン機能

- Firebase Authenticationの匿名アカウントと、任意のGoogleアカウント連携による同一UID保護・別端末復元
- トップページに通常型1on1・戦略型1on1・2on2・バトルロワイヤル別の対戦待機中・対戦中人数と、推し値市場の売り手待機・買い手待機人数・商談中件数をリアルタイム表示
- 通常型1on1・戦略型1on1・2on2・バトルロワイヤルを合算するデイリー・ウィークリー・マンスリーの上位50人オンライン総合ランキング（任意参加）
- 既存順位を期間途中で消さない段階移行。デイリーは`2026-07-24`、ウィークリーは`2026-07-27`、マンスリーは`2026-08`の期間キーから、Cloud Functionsが検証済み正式対戦だけを集計するサーバーランキングへ切り替え、それ以前の期間は終了まで従来表示を維持
- サーバーランキング終了後に保存されるランキング実績。デイリーは1試合で順位記録・TOP3、ウィークリーは3試合で参加記録・TOP10・TOP3・チャンピオン、マンスリーは10試合で参加メダル・TOP10・TOP3・チャンピオンを確定し、マンスリー1位は歴代王者として保存。ランキング実績からAnjuPay報酬は発生しない
- 4モードの確定済み最終結果から、自分の勝敗・モード固有の成果と正式URLだけを入力したX投稿作成画面を開く結果シェア
- 4モードの各準備画面とランキング画面に、参加・非参加、Xリンク、コメント受付をまとめた同一の展開式ランキングフォームを表示
- 勝利・バトルロワイヤル1位は3点、引き分け・バトルロワイヤル2位は1点、敗北・3位・4位は0点として集計
- 日本時間の日付・月曜始まりの週・月を期間キーとして使用し、期間切り替え後も4モード共通の総合RATEを維持
- 総合RATEを`Beginner / Great / Expert / Veteran / Ultra / Master / Legend`の7基本クラスに区分し、RATE 1400以上かつ当月マンスリー総合ランキング10位以内のプレイヤーだけを名誉クラス`BEYOND`として表示
- ランキング参加者同士で、相手1人につき1件・1行80文字以内のコメントを投稿・更新できるプレイヤーコメント
- コメント投稿者と投稿先プレイヤーによる削除、投稿先プレイヤーによるコメント受付ON/OFF
- 毎日0:00（日本時間）に更新される6つのデイリーミッションと、受取式のAnjuPay報酬（汎用の「1試合を完走」は2026年7月23日0:00に終了）
- 通常型1on1・戦略型1on1・2on2・バトルロワイヤルにはそれぞれ1回完走ミッションがあり、ルーム破棄・NO CONTESTは対象外
- 4モードの正式対戦を非公開のデイリー・ウィークリー・マンスリー戦績へ自動蓄積し、期間終了後にまとめて受け取れる期間戦績報酬。公開ランキングへの参加設定は不要で、勝利3・引き分け1の戦績スコアに応じて報酬額が上がり、必要試合数を満たせば敗戦時も基本報酬を獲得

## 画像とデータの扱い

- 選択画像は1on1では最大1600px、2on2・バトルロワイヤルでは4人転送の通信量を抑えるため最大1280pxに縮小してWebPへ変換します。
- Canvasを経由するため、元画像のEXIFなどの付随情報は引き継ぎません。
- 画像本体と画像IDは、両者がそのラウンドの選択をロックするまで相手へ送りません。
- オンライン画像はWebRTCで対戦相手へ直接送り、Firebase Realtime DatabaseやStorageへ保存しません。通常型1on1のフィニッシュセリフとシグネチャー判定はそのラウンドの画像転送メタデータ、決着返礼は敗者が応えた時の一時メッセージとして対戦相手だけへ送り、Firebaseの待機列・ルーム・プロフィールには保存しません。戦略型1on1と推し値市場の音声、戦略型1on1の短尺映像と品評会追加メディアもDataChannelで直接送り、Firebaseには保存しません。短尺映像は最大10秒・約2MBのWebMまたはMP4に限定し、申告MIMEだけでなく実データのヘッダーも確認します。品評会画像はWebPの実ヘッダー、品評会音声はRIFF/WAVE構造・モノラル16bit PCM・実データから再計算した時間を送受信時に確認します。推し値市場の出品画像も、ブラウザが申告するMIMEだけに依存せず、WebP・PNG・JPEGの実データ形式を送受信時に確認します。戦略型1on1と推し値市場は通常型1on1とは独立したルームでP2P転送し、2on2・バトルロワイヤルでは各ブラウザが残り3人とP2P接続します。
- プロフィール画像は中央を256px正方形のWebPへ変換して同一ブラウザのIndexedDBだけに保存します。通常型・2on2・バトルロワイヤルは対戦開始後、戦略型は「対戦相手、判明」以降だけ表示し、ランキング・トップページ・最終結果には表示しません。
- Xへの結果シェアは`https://gazostadium.anjugames.workers.dev/`を正式URLとして使用し、相手名・具体的な弱点・対戦画像・音声・チャット・匿名UIDを投稿文へ含めません。投稿内容はXの作成画面で本人が確認・編集し、通信エラーやNO CONTESTには共有ボタンを表示しません。
- 同じモード内で再戦する時は、自分の直前のデッキ画像、通常型1on1のシグネチャーカード指定、戦略型の添付音声を保持し、使用済み状態だけを戻してそのまま再編集・再利用できます。相手から受信した画像・音声・短尺映像、チャット、ルーム参照は再戦時に解放します。タイトル復帰・明示的なモード終了・ページ終了時は自分のデッキを含む対戦メディアのURL・Blob参照をすべて解放し、録画中ならカメラ・マイクの全トラックも停止します。自分のプロフィール画像だけは次回起動用として端末内に残します。
- Firebaseへ保存するのは匿名UID、任意連携したGoogleの認証識別子、表示名、追撃セリフ、本人が任意公開した推しカード、通常型・戦略型1on1待機中の自己申告による採点傾向と検索範囲、戦略型1on1の弱点候補・弱点コミット・回答確定後の弱点公開値、品評会への回答・開始時刻・終了状態、2on2のTEAM LINK作戦、モード別戦績、非公開の総合戦績、公開設定時の期間別総合ランキング戦績、ランキングコメント、通常型1on1のサンプル枚数・開始HP、チーム分け、ルーム状態、点数、チャット本文・スタンプIDなどの対戦メタデータです。通常型1on1のフィニッシュセリフ、決着返礼、口調セット、シグネチャーカード情報はFirebaseへ保存しません。Googleの名前・メールアドレスはゲーム内表示名、対戦、ランキングへ使用・公開しません。通常型・戦略型の採点傾向は待機キューから退出した時点で削除し、共有ルームへ複製しません。スタンプ画像本体は静的WebPでありFirebaseへ保存・送信しません。推しカードの公開キーには匿名UIDではなく専用のランダムIDを使用し、公開情報は表示名、活動札、紹介文、投稿時の称号、選択した実績、成長段階、許可したXユーザー名だけです。戦略型チャットには送信者UID、本文、匿名探索中・対戦中・品評会中の区分、ラウンド、送信時刻を保存し、正体判明後の発言だけ装備中の装飾IDも保存します。短尺映像・プロフィール画像の本体は保存しません。戦略型の待機キューにはUIDと時刻・待機状態・採点傾向・検索範囲だけを置き、弱点番号そのものは両者が回答するまで共有ルームへ保存しません。推しカード紹介文は1行30文字以内、追撃セリフは1行40文字以内、フィニッシュセリフは1行30文字以内、決着返礼は最大40文字・改行1回以内、各チャットとランキングコメントは1行80文字以内に制限し、画面ではHTMLとして実行せず文字列として表示します。
- ミッション進捗、期間戦績報酬、日付・段階別のデイリープレイ報酬台帳、報酬済み試合ID、実績進捗・解除済み実績、サーバーランキング参加状態・期間戦績・確定実績、AnjuPay残高、差し入れ台帳、推し値証書、推し値商店、常連帳、ブロック関係、肯定タグ台帳の正本はCloud Firestoreのサーバー専用領域へ保存します。対戦終了時は参加者本人だけが一度書ける結果申告をルームへ残し、Cloud Functionsが全参加者の申告整合、参加者・プロフィール・承認人数、本人が書いた採点証跡、12時間以内のアクティブルームを確認した場合だけ加算します。デイリープレイ報酬はこの検証済み日次戦績だけを参照し、段階ごとの一意台帳とウォレットを同じトランザクションで更新します。差し入れは検証済み試合台帳と両者の参加を再確認し、送信者・モード・ルームの一意台帳と両ウォレットを同じトランザクションで更新します。重複防止IDは件数で削除しないFirestore台帳へ永続保存します。既存の検証済み月間戦績から通算・モード別・敗北・対戦日数を遡及しますが、試合順を復元できない連敗は実績導入後から数えます。Realtime Databaseのミッション・期間戦績・AnjuPay残高・サーバーランキングは表示用ミラーで、クライアントから変更できません。購入済み商品と装備設定はRealtime Databaseの匿名UIDごとの非公開領域へ保存します。装備中の称号・チャット背景・チャットフレーム・購入スタンプのIDだけは、チャット送信時に同じルームの参加者へ共有します。戦略型1on1の匿名偵察中は装飾IDを送信せず、無料スタンプIDだけを許可します。
- トップページの参加状況には人数・件数だけを表示し、閲覧者は含みません。推し値市場は参加ごとに発行するランダム公開ID、ロール別の最終通信時刻、競合防止用の状態世代だけを公開領域へ反映し、60秒以内に通信した待機者と、売り手・買い手の双方が60秒以内に通信した商談だけを集計します。本人が任意公開した推しカードには、匿名UID、勝敗、RATE、画像、ルーム履歴、Googleアカウント情報を含めません。
- ランキング参加者はプレイヤーネーム・総合RATE・動的算出するクラス・選択期間の総合戦績、合計スコア、モード別スコアを公開します。基本クラス境界は`Beginner 100–1024 / Great 1025–1049 / Expert 1050–1099 / Veteran 1100–1149 / Ultra 1150–1199 / Master 1200–1299 / Legend 1300–3000`です。`BEYOND`はRATE 1400以上かつ当月マンスリー総合ランキング10位以内の間だけLegendに代わって表示し、Firebaseへ固定保存しません。すべてのクラスは待機室・対戦・チャット・結果画面には表示しません。サーバー化時の総合RATEは旧RATEを初期値として引き継ぎ、以後は検証済み正式対戦だけで更新します。デイリーは毎日0:00、ウィークリーは毎週月曜0:00、マンスリーは毎月1日0:00（日本時間）に新しい期間キーへ切り替わります。本人が個別に許可した場合だけ、Xのユーザー名と自分宛てのコメントも公開します。

ブラウザに表示した画像は、相手によるスクリーンショット、開発者ツール、画面撮影まで技術的に完全防止することはできません。「ゲーム自身が画像ファイルを保存・配布する機能を持たない」という範囲の保護です。

## Firebase構成

このリポジトリはFirebaseプロジェクト `gazostadium` 用に設定済みです。

- Authentication: 匿名ログインを基本とし、任意のGoogle連携と引き継ぎ用Custom Tokenで同一UIDを別端末へ復元
- Realtime Database: 各対戦モードのマッチング、ルーム同期、チャット、戦績、トップページ用の匿名化済み参加状況と推しカード公開ミラー、推し値市場のチャット・WebRTCシグナリングに使用
- Cloud Firestore: 権威ウォレットとAnjuPay利用履歴、サーバー検証済みミッション・期間戦績・試合台帳、差し入れ台帳、推し値市場の待機列・取引状態・移動台帳・独立ランキング・証書・推し値商店・常連帳・ブロック・肯定タグ、月間パトロン・循環基金・方針投票・推薦枠、ハッシュ化した短期引き継ぎコードに使用
- Cloud Functions（`us-central1`）: `nam5`のCloud Firestoreに近接し、AnjuPay報酬・ストア購入・推しカードの公開・削除・成長同期・プレミアム権利確認、市場取引・推し値商店の公開情報・常連優先照合・肯定タグ・ブロック・成約手数料と基金補填・証書発行・対戦後差し入れ・パトロン支払いと方針投票・推薦・使い捨て引き継ぎをサーバー権限で確定
- Storage: 使用しない
- Firebase Hosting: `https://gazostadium.web.app` で本番公開
- クライアント設定: `firebase-config.js`
- セキュリティルールの管理元: `database.rules.json` / `firestore.rules`
- Firebase CLI設定: `.firebaserc` / `firebase.json`（既定プロジェクト `gazostadium`）

Realtime Databaseのルールは、各ユーザーが自分の待機情報・採点・順位投票・モード別戦績・総合戦績・移行前の期間別ランキング・一度限りの対戦結果申告だけを書けること、各ルームの参加者だけがルーム情報を読めることを制約します。期間キーがサーバー切替日以降のランキング、AnjuPay残高、デイリー進捗、購入済み商品、期間戦績報酬、ランキング実績、報酬済みルーム台帳、推しカード本体・所有者・ユーザー別公開IDへのクライアント直接書き込みは禁止し、Cloud FunctionsのAdmin SDKだけが更新します。推し値市場の公開参加状況もクライアント書き込みを禁止し、Functionsが参加単位のランダムIDと集計に必要なロール・最終通信時刻・状態世代だけを更新します。推し値市場のRealtime Databaseルームは、取引中の参加者本人のチャット・接続状態と、相手宛てWebRTCシグナルだけを書けます。終了後は新規投稿を拒否し、シグナル削除とオフライン化だけを許可します。市場の取引状態・ウォレット・ランキング・推し値商店・常連帳・ブロック関係・売り手買い手ペア・肯定タグ台帳・パトロン循環基金・補填台帳・月間方針投票・推薦枠はFirestore Rulesでクライアントの直接読み書きを全面禁止し、Callable Functionsだけが本人の権限、App Check、成約履歴を検証して更新します。任意公開プロフィールもFunctionsが本人の実績ドキュメントへだけマージします。ランキング、推薦棚、店主カードの応答には匿名UIDを含めず、表示名・ゲーム内店コード・必要な実績・本人が公開した項目だけを返します。Firebaseコンソールでルールを変更する場合は、リポジトリ内の両Rulesも同じ内容に保ってください。

通常版1on1は、Functionsが発行する60秒リースとセッション世代を使うV2待機列へ移行します。ルーム、招待、active、permit、lockはFunctionsだけが生成し、シグナルと対戦中の書き込みはルームに固定されたセッション世代と現在のリースが一致する場合だけ許可します。同じ匿名アカウントを別タブ・別端末から使った場合は新しい対戦を並行開始せず、同一タブ複製の引き継ぎもBroadcastChannelで旧ページが応答しないことを確認してから行います。接続開始から15秒で一度だけICE restartを行い、それでも接続できない場合はルームを完全に片付けてから一度だけ別相手を自動検索します。いったんDataChannelが開いた対戦、手動取消、非表示ページ、オフライン状態では自動再検索しません。

通常版1on1のICE設定は認証・App Check済みの`getP2pIceServers`がCloudflare Realtime TURNの短期資格情報を返します。長期API tokenとTURN key IDはSecret ManagerからFunctionsだけが読み、ブラウザ、Realtime Database、ログへ保存しません。`reportP2pConnectivity`は接続状態、候補種別、transport、所要時間だけを許可し、IP、SDP、ICE candidate、User-Agent、UID、任意フィールドを拒否します。保存時は日ごとのHMACへ置き換え、診断本文と日付インデックスは最低14日が満了した後、書込み時の保守処理とJST 03:30の日次`cleanupP2pDiagnostics`で日単位に段階削除します。

通常型1on1の顔なじみ希望・相互関係・ブロック・再会間隔はFirestoreのサーバー専用領域へ保存し、クライアントから直接読み書きできません。Callableの帳面・非表示管理はランダムな40桁IDと表示名だけを返し、相手UIDや相手側の選択を返しません。再会段階ではFunctionsが候補とブロックを再確認し、期限付きpermit、両者lock、完全なルームと招待をサーバー側で作成します。クライアントは有効なpermit・両lock・招待が揃った時だけ招待済みから対戦中へ進めます。クライアントの再会確認は即時反映用ですが、確認送信を省略しても次のマッチング前に期限付きlockとpermitをFunctionsが回収し、対戦中への遷移を確認して再会優先の24時間間隔を記録します。通信失敗時はpermitを先に消さず、次回の回収へ残します。なお通常型1on1の既存マッチング、ルーム、WebRTCシグナルは対戦相手を識別するため認証UIDを内部通信キーとして使用しており、UIDそのものを全認証ユーザーから秘匿する設計ではありません。

## Firebaseへデプロイする

初回だけFirebaseコンソールでCloud Firestoreの本番データベースを作成し、`functions`フォルダーで依存関係をインストールします。

```powershell
npm --prefix functions install
npx --yes firebase-tools deploy --only firestore,database --non-interactive
npx --yes firebase-tools deploy --only functions --non-interactive
npx --yes firebase-tools deploy --only hosting --non-interactive
```

初回はこの順番を守り、先にクライアントからのAnjuPay残高・デイリー進捗・期間戦績報酬への直接書き込みをRulesで閉じてから、Functionsと新しいフロントエンドを公開します。旧版のRealtime DatabaseにあるAnjuPay残高と購入済み商品は最初のFunctions利用時に一度だけFirestoreへ移行しますが、旧ルール下で作られた値の正当性を後から完全には判別できません。公開前にRealtime Databaseをエクスポートして異常な高残高・大量商品を確認してください。デイリー進捗と期間戦績は安全のため旧値を移行せず、新しいサーバー台帳から開始します。

推しカード版を既存本番へ追加するときは、新しい`economyAction`と`valueMarketAction`を先に配備し、その後にRealtime Database RulesとHostingを配備します。旧商品ID `feature_top_message` を変更しないため購入権はそのまま引き継がれ、Functions配備後も旧クライアントの公開ひとことは新しいRulesへ切り替わるまで利用できます。

### 通常版1on1 V2・TURNの公開

Cloudflare Realtime TURNで作成したサーバーのkey IDとAPI token、および32byte以上のランダムな診断HMAC secretを、値をファイルへ残さずFirebase Secret Managerへ登録します。secret名は次の3つで、値そのものはGit、`.env`、README、デプロイログへ記載しません。

```text
CLOUDFLARE_TURN_KEY_ID
CLOUDFLARE_TURN_API_TOKEN
P2P_DIAGNOSTIC_HMAC_SECRET
```

本番切替は、旧クライアントを止めないため次の順番で行います。

1. Cloudflareの短期ICE credential APIがHTTP 201を返し、STUNとTURN/TURNSの両方を含むことを運営環境から確認する。
2. `soloSessionAction`、`getP2pIceServers`、`reportP2pConnectivity`、日次削除の`cleanupP2pDiagnostics`に加え、旧matcherとの相互フェンスを持つ`soloFamiliarAction`とV2対戦中の移行を拒否する`accountTransfer`を先に配備する。新規3 Callableは段階設定に関係なくApp Checkを常時強制するため、本番ドメインの正規通信がVerifiedであることを確認する。
3. `database.rules.json`を配備する。V2 claimが存在しない旧クライアントはlegacy経路を継続できる。
4. 新旧Functions revisionの入れ替わり中に旧matcherとV2 matcherが交差しないよう、Functions配備完了から90秒以上待つ。この間はHostingを配備せず、`soloSessionAction`の正規呼び出しが新revisionで成功することを確認する。
5. `p2p-hardening-v2`のキャッシュキーを含むHostingを配備する。
6. Wi-Fi同士だけでなく、家庭Wi-Fi対モバイル回線、iPhone Safari対PCブラウザでも2アカウントの成立、取消、ページ再読込、同一アカウントの別タブ拒否、15秒timeout後の一度だけの再試行を確認する。診断で`candidateType: relay`が記録される試験も1件確認する。

```powershell
npx --yes firebase-tools deploy --only functions:soloSessionAction,functions:getP2pIceServers,functions:reportP2pConnectivity,functions:cleanupP2pDiagnostics,functions:soloFamiliarAction,functions:accountTransfer --non-interactive
npx --yes firebase-tools deploy --only database --non-interactive
Start-Sleep -Seconds 90
npx --yes firebase-tools deploy --only hosting --non-interactive
```

切り戻す場合はHostingを先に旧版へ戻し、V2クライアントが止まってから90秒以上待ちます。V2のFunctionsとRulesは旧クライアントと互換なので、障害調査中は残して構いません。Rulesを先に旧版へ戻すと、配信済みV2クライアントの待機・シグナル・cleanupが拒否されるため避けます。

AnjuPay履歴を既存本番へ導入するときは、旧Functionsインスタンスが履歴を記録しないまま残高を更新する時間帯を作らないため、事前準備後に三段階で有効化します。

0. Functionsを配備する前に、Firestoreへ`systemConfig/anjuPayLedger`を`{ enabled: false, activatedAt: 0 }`で作成します。初回配備に限ってGit管理外の`functions/.env.gazostadium`へ`ANJU_PAY_LEDGER_REQUIRED=false`を設定します。設定documentがない場合や、このパラメータを設定せず既定値`true`のまま配備した場合、台帳対応Functionsは残高操作をfail-closedで拒否します。
1. 上記の無効状態・互換パラメータのまま、AnjuPay履歴に対応したFunctionsとFirestore Rulesを先に配備します。
2. Functionsの配備完了後、旧インスタンスのドレイン時間として30秒を超えて待ち、同じdocumentへ`enabled: true`と`activatedAt: <現在のUnix epochミリ秒>`を同時に設定します。この時点ではまだHostingを配備しません。
3. Hostingの前に`ANJU_PAY_LEDGER_REQUIRED=true`へ変更して全Functionsを再配備し、もう一度30秒を超えて旧インスタンスのドレインを待ちます。デプロイ済みrevisionの実行時パラメータが実際に`true`であることを確認してからHostingを配備し、以後このパラメータを`false`へ戻しません。マーカーが有効なら互換revisionでも通常操作は成功するため、画面のスモークテストだけでは確認完了にしません。

有効化前の増減を後から推測して埋めません。有効化後に各ウォレットへ「AnjuPay開始残高」を一度だけ記録し、以後の全増減を同じ残高更新トランザクションで追記します。

`activatedAt`は一度設定したら変更・削除しないone-wayマーカーです。有効化後は台帳非対応の旧Functions revisionや互換パラメータのrevisionへロールバックしないでください。`enabled`を誤って`false`にしても`activatedAt`が残る限り記帳は継続し、台帳必須revisionでは設定documentの削除、完全な無効状態への巻き戻し、`activatedAt`の消去、または`enabled: true`だけの不完全な設定を新規ウォレットも含めてfail-closedにします。緊急時は経済系Callableへのトラフィックを止め、台帳必須revisionを基点に修正版を配備します。詳細は`functions/ANJU_PAY_LEDGER_ROLLOUT.md`を参照してください。

既存の推し値市場へ待機セッション版を反映するときは、先に`firestore:indexes`だけをデプロイし、Firebase Consoleで`role,status,matchMode,maxBudget,lastSeen`、`role,status,listing.askingPrice,lastSeen`、`selectedFavoriteSellerUid,status,lastSeen`、`preferredSellerUid,status,lastSeen`の4件が`READY`になったことを確認してから市場Functionsをデプロイします。最後のインデックスはパトロン推薦棚の20秒ソフト優先に使います。旧Functionsが使う`role,lastSeen`インデックスは互換期間のため定義に残してあり、Functions切替と同時には削除しません。

サーバーランキング版を既存本番へ追加するときは、先に`economyAction`を公開し、その直後にRulesとフロントエンドをまとめて公開します。新しいフロントエンドは登録用Callableを必要とし、新しいRulesは切替日以降のクライアントランキング書き込みを拒否するため、この順番を変えないでください。

```powershell
npx --yes firebase-tools deploy --only functions:economyAction --non-interactive
npx --yes firebase-tools deploy --only database,firestore:rules,hosting --non-interactive
```

最初の切替日までに公開しない場合は、過去日付のまま公開しないでください。`functions/server-ranking.js`、`online.js`、`database.rules.json`、テスト、上記READMEの切替キーを、公開後に到来する次の日次・月曜・月初へ同時に繰り下げます。サーバー版公開前の試合はランキングへ遡及加算しません。

### 顔なじみ帳・再会マッチングの段階公開

顔なじみ機能はFirestoreの`systemConfig/soloFamiliarRollout.stage`とRealtime Databaseの`online/config/soloServerMatchmaking`で二重に制御します。設定documentがない場合、または不明な値の場合は`engawa_only`へ閉じます。`stage: reunion`でもRealtime Databaseの権威フラグが厳密な`true`でなければ実効段階は`familiar_book`です。`soloFamiliarAction`は他のCallableの段階設定に関係なくApp Checkを常時強制します。

1. `firestore.indexes`だけを先に配備し、`soloFamiliarPairs`の`participants CONTAINS + active ASC`複合インデックスが`READY`になり、`soloFamiliarIntents`・`soloFamiliarPairs`・`familiarEntries`・`soloFamiliarReunions`の`deleteAt` TTLが有効になったことを確認します。
2. `soloFamiliarAction`、Firestore Rules、Realtime Database Rulesを同じソースから配備します。この時点ではFirestore設定を未作成または`engawa_only`、Realtime Databaseの権威フラグを未作成または`false`のままにします。
3. `solo-familiar-v1`のキャッシュキーを含むHostingを配備し、通常型1on1の縁側、通常マッチング、取消、再読込を2アカウントで確認します。戦略型1on1・2on2・バトルロワイヤルも回帰確認します。
4. 反応を確認してからFirestoreを`stage: familiar_book`へ進め、片側希望、相互希望、削除、ブロック、非表示管理のページ送りを確認します。
5. 再会を試す時は先にFirestoreだけを`stage: reunion`へ進めます。権威フラグが`false`の間は実効段階が`familiar_book`のままであることを確認し、その後にRealtime Databaseの`online/config/soloServerMatchmaking`を`true`へ変更します。顔なじみ優先・24時間間隔・通常相手への即時フォールバック・招待取消を確認します。

再会を戻す時は、最初にRealtime Databaseの権威フラグを`false`へ戻し、その後Firestoreを`familiar_book`または`engawa_only`へ戻します。順序を逆にしないでください。権威フラグを戻すと既存の通常マッチャーへ復帰するため、ブロックは顔なじみ帳と再会優先からは外しますが、通常検索での偶然の再会防止は保証しません。

現在の再会マッチャーは小規模な段階検証を前提に、3秒の補助pollとサーバー側の待機列確認を使います。全面公開前にFunctionsの呼出数・p95実行時間・エラー率、待機人数、permit/lock残留、通常相手へ戻る割合を監視してください。人数増加時は待機列のbucket化とUID別lock仲裁へ移行し、全待機列読取と単一lockルートの競合を解消してから対象を広げます。

Google保護を本番で利用する前に、Firebase ConsoleのAuthenticationで匿名認証を維持したままGoogleプロバイダを有効化し、サポートメールを設定します。WorkerやGitHub Pagesで公開する場合は、それぞれのHTTPSホスト名をAuthenticationの承認済みドメインへ追加してください。`accountTransfer`は`consumeAppCheckToken: true`を常時指定しているため、第2世代Functionsの実行サービスアカウントへFirebase App Check Token Verifierロールが必要です。Custom Token作成に既定外のサービスアカウントを使う構成では、Firebase Admin SDKのトークン署名に必要なIAM権限も確認してください。

App CheckはreCAPTCHA Enterpriseを使用します。`firebase-client.js`が全モード共通のFirebase AppとApp Checkを初期化し、その後`firebase-services.js`がAuth・Realtime Database・Firestore・Functionsを生成します。サイトキーは`firebase-config.js`の`appCheckRecaptchaEnterpriseSiteKey`へ設定します。初回リリースでは強制せず、3本番ドメインで最新版を配信してから、App Checkの`Verified`比率とFunctionsログを監視します。localhostから本番バックエンドへ接続してデバッグトークンを使う場合だけ`?appCheckDebug=1`を付けます。`?firebaseEmulators=1`と`?marketPreview=1`では本番App Checkを初期化しません。

強制適用は「経過日数」ではなく、実通信の確認結果を基準にします。各ドメインで通常型・戦略型・2on2・ロイヤル・推し値市場、ショップ、デイリー、期間報酬、ランキングコメントを能動テストし、正規通信が概ね99%以上`Verified`で、`Outdated client`と`Invalid`に正規ユーザーが含まれないことを確認します。サービスごとの推奨順は次のとおりです。

1. Firestoreを強制し、反映後15分以上待ってVALUE MARKETを再確認する
2. `functions/app-check-rollout.js`の段階を`rankings_enforced`へ進め、`firebase deploy --only functions:valueMarketRankings`で個別デプロイする
3. 段階を`market_migration`へ進め、`valueMarketQueue`と`valueMarketAction`を再デプロイする。未検証クライアントの新規参加・heartbeatを止め、検証済みの新規ルームを保護しながら、旧ルームの完了経路は残る
4. `valueMarketRooms`の非終端ルームを一覧し、`appCheckVerified: true`でないもの（フィールド未設定を含む）が0件になるまで待つ
5. 段階を`market_enforced`へ進めて`valueMarketAction`と`valueMarketQueue`を強制し、その後`economy_enforced`へ進めて`economyAction`を最後に強制する
6. 全オンラインモードが依存するRealtime Databaseを最後に強制する

Callableは`APP_CHECK_ROLLOUT_STAGE`の1値から関数別の強制設定を導出し、市場関数の片側だけを強制するような不整合な設定を作らない構成です。市場待機列と市場ルームには`appCheckVerified`を記録するため、移行前から作られた取引を判別できます。段階は必ず記載順に進め、各段階を低利用時間帯に行い、反映後15分以上のスモークテストと24時間程度の監視を挟みます。問題があればFirestore・Realtime Databaseはコンソールで監視へ戻し、Callableは段階を直前の値へ戻して対象関数だけ再デプロイします。

本番URL: `https://gazostadium.web.app`

ローカルでAuthentication・Functions・Firestore・Realtime Databaseをまとめて検証する場合は、別ターミナルで次を起動し、`http://127.0.0.1:4173/?firebaseEmulators=1`を開きます。このクエリはlocalhostでだけ有効です。誤って本番データへ接続しないよう、必ず`demo-`で始まる架空プロジェクトIDを使用します。Database・Firestore Emulatorの起動にはJavaが必要です。

```powershell
npx --yes firebase-tools emulators:start --only auth,functions,firestore,database --project demo-gazostadium
```

Javaを用意できない環境で画面レイアウトだけを確認する場合は、`?marketPreview=1`で500 Payの市場ローカルプレビューを開けます。市場プレビュー一覧の「推し嬢クロージング画面」から、買い手向けの注意・総支出・二段階購入確認・見送り導線を確認できます。同じプレビューからAnjuPayストアを開くと、2,500 Payと「推し活・ときめきコレクション」の購入・装備例、推しカード編集ルームへ移動したことを知らせる案内を読み取り専用で表示します。トップページの「自分のカードを飾る」からは、推しカードの成長段階、無料4テーマ、プレミアム3テーマの試着と買い切り案内を確認できます。トップからAnjuPayウォレットを開くとゲスト状態を確認でき、`?marketPreview=1&accountPreview=protected`ではGoogle保護済み・6,400 Payの表示を確認できます。プレビューはFunctionsやデータベースへ接続せず、認証・取引・AnjuPay支払い・装備変更・推しカード公開・引き継ぎ確定テストには使用しません。

未購入状態の試着導線を確認する場合は、`?marketPreview=1&creatorCardPremium=locked`で推しカード編集ルームを開きます。プレミアム3テーマを自分のカードへ試着し、500 Payの一括解放案内、試着中の公開・画像保存・共有停止、残高表示を確認できます。このfixtureも見た目専用で、実際の購入やAnjuPay消費は行いません。

## GitHub Pagesで公開する

1. このフォルダーをGitHubリポジトリへpushします。
2. GitHubのリポジトリで `Settings` → `Pages` を開きます。
3. `Deploy from a branch` を選び、公開ブランチのルートを指定します。
4. 発行されたHTTPS URLへ2つのブラウザ環境からアクセスし、マッチングを確認します。

GitHub Pagesにはフロントエンドの静的ファイルだけを配置できますが、オンライン対戦と推し値市場を動かすには、同じFirebaseプロジェクトへRealtime Database Rules・Firestore Rules/Indexes・Cloud Functionsを別途デプロイする必要があります。FirebaseのWebクライアント設定は公開される前提の識別情報であり、アクセス制御は両データベースのRulesとCloud Functionsが担当します。

## 現時点の制約

- 通常版1on1はCloudflare Realtime TURNを利用します。TURN自体の障害、FunctionsまたはApp Checkの拒否時は公開STUNへ安全に縮退するため、その間は厳しいNATや組織ネットワーク同士で接続できない場合があります。戦略型1on1、推し値市場、2on2、バトルロワイヤルは現時点では従来どおりSTUN中心です。戦略型の短尺映像と品評会追加メディアはDataChannelが利用できない時に該当メディア送受信だけを無効にし、品評会チャットや対戦進行は継続します。3接続が必要な2on2・バトルロワイヤルは、1on1より接続失敗の影響を受けやすくなります。
- Google保護または引き継ぎを行っていない匿名アカウントはブラウザのサイトデータに紐づき、サイトデータを消すと復元できません。Google保護後はUIDに保存したオンラインデータを復元できますが、端末保存したプロフィール画像・対戦素材・音声・設定は対象外で再登録が必要です。
- 採点の書き換え先はセキュリティルールで本人の領域に限定していますが、通常対戦の採点・勝敗自体は完全な権威サーバー方式ではありません。
- サーバー切替日より前に始まったオンライン総合ランキングは従来のカジュアル表示で、期間終了まで現在順位を維持します。この移行前データへランキング実績やAnjuPay報酬を後付けしません。切替日以降はCloud Functionsが検証済み試合台帳から期間戦績とRATE変動を確定し、Realtime Databaseには匿名UIDを含まない公開ミラーだけを書きます。ランキング実績は名誉記録でAnjuPay報酬を発生させません。AnjuPayを発行するデイリー・期間戦績と、推し値市場のAnjuPay移動・独立ランキングもCloud Functionsで確定します。
- サンプル画像のHPハンデもクライアントとRealtime Database Rulesで整合性を確認するカジュアル版です。改造したクライアントがサンプル画像を通常画像として偽装することまでは完全に防止できません。
- ランキング・市場プロフィール・推しカードのXリンクは自己申告で、アカウント所有者の本人確認は行いません。Xを公開すると匿名性が下がります。
- ランキングコメントは公開情報です。URLと改行は画面側で拒否し、ルールでも1行80文字以内に制限しますが、自動モデレーションや通報機能はまだありません。
- 推しカードも公開情報です。紹介文のURL・メールアドレス・改行と未解除実績、不正なテーマはCallable Functionsで拒否し、Realtime Databaseの公開領域はクライアントから直接変更できません。閲覧者単位の非表示には対応しますが、自動モデレーションや運営向け通報画面はまだありません。
- 採点系ミッション、期間戦績、デイリープレイ段階報酬は、Functionsが全参加者の一度限りの結果申告、本人が書いた採点証跡、実在ルームの参加・完走・重複を検証します。ただし匿名認証である以上、複数端末・複数匿名アカウントを本人確認なしに完全排除することはできません。同一相手との異常な短時間周回、モード別完走時間、AnjuPay発行量はFunctionsログで継続監視してください。報酬受取・ストア購入・市場内のAnjuPay残高移動はFirestoreウォレットの上限・予約受取枠・価格・取引状態・冪等操作IDを検証します。クライアントからAnjuPay残高、デイリー進捗、購入済み商品、期間戦績報酬を直接書き換えることはできません。
- 推し値市場の同一ペア日次除外は単純な相互売買のランキング水増しを抑えますが、複数の匿名アカウントを用いた組織的な取引までは完全に識別できません。App Check有効化とFunctionsログの監視を推奨します。
- 終了済みルームのメタデータは管理用の定期削除をまだ実装していません。画像本体はルームに保存されません。
